# 订单拆单与多发货履约模式方案 v2.0

## 1. 文档说明

本文档用于在现有 `WMS-API接口清单.md` 基础上，补充“一个电商订单拆分为多张发货履约单，且不同发货履约单可采用不同履约模式”的整体方案。

本方案为独立版本方案文档，不直接覆盖现有正式文档，待方案评审通过后，再统一回写接口清单、系统交互图与流程图。

核心目标如下：

- 支持一个电商订单拆分为多张发货履约单
- 支持不同发货履约单采用不同履约模式：`INSTANT`、`EXPRESS`
- 明确订单商品行与发货履约单之间的映射关系
- 明确拆单责任边界、回调聚合规则与后续文档调整范围

## 2. 背景与问题

现阶段已明确：

- WMS 对外统一面向“第三方电商系统”开放
- 订单发货执行主对象为“发货履约单”
- 即时配送与快递配送属于两种不同的履约模式

但在实际业务中，存在以下场景：

- 一张电商订单中的不同商品，需要采用不同履约模式
- 同一订单中，部分商品适合即时配送，部分商品适合快递配送
- 不同商品可能来自不同仓、不同履约策略或不同包裹策略

若仍采用“整张订单只有一个履约模式”的方案，会产生以下问题：

- 无法表达同单多模式履约
- 包裹、轨迹、异常、回调都无法准确归属
- 上游电商系统和 WMS 的执行主对象边界不清晰

因此，需升级为“订单主单 + 多发货履约单”模型。

## 3. 方案结论

### 3.1 总体结论

- 一个 `order_id` 可对应多张 `shipment_order_id`
- 一张 `shipment_order_id` 只能对应一种 `fulfillment_mode`
- `fulfillment_mode` 归属于发货履约单，不归属于订单主单
- 拆单维度为“按商品行拆分”，不支持“按数量拆分”
- WMS 回调以发货履约单为主键，上游电商系统负责汇总订单主单状态

### 3.2 标准模型

```text
订单主单（order_id）
  -> 发货履约单 A（shipment_order_id=A, fulfillment_mode=INSTANT）
     -> 商品行 1
     -> 商品行 2
  -> 发货履约单 B（shipment_order_id=B, fulfillment_mode=EXPRESS）
     -> 商品行 3
     -> 商品行 4
```

### 3.3 不支持的场景

以下场景不纳入本期标准方案：

- 同一商品行按数量拆分到多张发货履约单
- 同一张发货履约单同时存在两种履约模式
- 由 WMS 在接单后自主猜测履约模式
- 由 WMS 在没有商品行归属信息的情况下自动推断拆单结构

## 4. 核心对象关系

### 4.1 对象定义

| 对象     | 主键                  | 说明                                    |
| ------ | ------------------- | ------------------------------------- |
| 电商订单主单 | `order_id`          | 电商系统中的用户订单主对象，用于业务归集与订单级展示            |
| 订单商品行  | `order_line_no`     | 电商订单中的商品明细行，是拆单最小颗粒度                  |
| 发货履约单  | `shipment_order_id` | WMS 对外履约执行主对象，是发货、出库、包裹、轨迹、异常、回调的核心主体 |
| 履约模式   | `fulfillment_mode`  | 发货履约单的履约方式，标准值为 `INSTANT` / `EXPRESS` |
| 包裹     | `package_id`        | 发货履约单下的包裹对象，用于承接拆单、合单、物流轨迹、面单等信息      |

### 4.2 对象归属规则

| 规则                | 说明                         |
| ----------------- | -------------------------- |
| 一个订单主单可对应多张发货履约单  | 用于承接同单多模式履约、多包裹策略或不同履约分组   |
| 一个发货履约单只能对应一种履约模式 | 避免一张履约单内部出现两套物流状态机         |
| 一个商品行只能归属一张发货履约单  | 与菜鸟云仓“按商品拆分、不按数量拆分”规则保持一致  |
| 一个包裹只能归属一张发货履约单   | 包裹查询、轨迹查询、面单获取都以发货履约单为上级对象 |

## 5. 拆单规则

### 5.1 拆单原则

订单拆单不是按订单总量拆，而是按“商品行履约归属”拆。电商系统在订单源头应先完成以下判断：

- 商品行归属哪个发货履约单
- 该发货履约单采用哪种履约模式
- 同一组商品行是否可合并为同一张发货履约单

### 5.2 拆单标准

| 拆单维度    | 是否支持        | 说明                      |
| ------- | ----------- | ----------------------- |
| 按商品行拆分  | 是           | 同一订单的不同商品行，可归属不同发货履约单   |
| 按数量拆分   | 否           | 同一商品行数量不可拆分到多张发货履约单     |
| 按履约模式拆分 | 是           | 即时配送与快递配送必须落在不同发货履约单上   |
| 按仓库拆分   | 是           | 如不同商品行由不同仓履约，可拆为不同发货履约单 |
| 按货主拆分   | 原则上不支持同单混货主 | 标准版 WMS 一张订单建议只服务同一货主   |

### 5.3 标准拆单示例

#### 示例一：同单双模式履约

```text
order_id = O2025001

商品行 1：常温日用品 -> EXPRESS
商品行 2：常温日用品 -> EXPRESS
商品行 3：门店现货鲜食 -> INSTANT

拆单结果：
shipment A -> 行 1、行 2 -> fulfillment_mode = EXPRESS
shipment B -> 行 3 -> fulfillment_mode = INSTANT
```

#### 示例二：不允许按数量拆分

```text
order_id = O2025002

商品行 1：SKU-APPLE，数量 5

不支持：
shipment A -> SKU-APPLE 数量 2 -> INSTANT
shipment B -> SKU-APPLE 数量 3 -> EXPRESS

原因：
同一 order_line_no 不允许拆数量归属到多张发货履约单
```

## 6. 订单商品行与发货履约单的对应关系

### 6.1 核心结论

订单商品行是拆单的最小履约归属颗粒度。每一个 `order_line_no` 在订单发货流程中，必须且只能归属到一张发货履约单。

### 6.2 映射关系模型

```text
order_id
  -> order_line_no_1
  -> order_line_no_2
  -> order_line_no_3

shipment_order_id_A
  -> order_line_no_1
  -> order_line_no_2

shipment_order_id_B
  -> order_line_no_3
```

### 6.3 映射规则

| 规则                  | 说明                                        |
| ------------------- | ----------------------------------------- |
| 一个订单主单包含多条商品行       | 每条商品行通过 `order_line_no` 唯一标识              |
| 每条商品行必须有唯一的发货履约归属   | 需映射到一张且仅一张 `shipment_order_id`            |
| 一张发货履约单可包含多条商品行     | 只要这些商品行履约模式一致、履约分组一致，即可聚合到一张发货履约单         |
| 商品行与履约模式通过发货履约单间接关联 | 不建议直接把 `fulfillment_mode` 挂在商品行上作为最终执行主字段 |

### 6.4 建议数据结构

建议在订单发货请求或内部履约建模中引入如下结构：

| 字段                  | 说明                       |
| ------------------- | ------------------------ |
| `order_id`          | 电商订单主单号                  |
| `order_line_no`     | 订单商品行号                   |
| `shipment_order_id` | 发货履约单号                   |
| `shipment_group_no` | 发货分组号，用于表示商品行先被分到哪个履约组   |
| `fulfillment_mode`  | 该发货履约单的履约模式              |
| `split_reason`      | 拆单原因，如履约模式不同、仓库不同、时效策略不同 |

### 6.5 推荐映射表

| order\_id | order\_line\_no | sku\_code | quantity | shipment\_group\_no | shipment\_order\_id | fulfillment\_mode | 说明         |
| --------- | --------------- | --------- | -------- | ------------------- | ------------------- | ----------------- | ---------- |
| O2025001  | 1               | SKU-A     | 1        | G1                  | S2025001-1          | EXPRESS           | 常温商品，走快递   |
| O2025001  | 2               | SKU-B     | 2        | G1                  | S2025001-1          | EXPRESS           | 与行 1 同组    |
| O2025001  | 3               | SKU-C     | 1        | G2                  | S2025001-2          | INSTANT           | 门店现货，走即时配送 |

### 6.6 映射处理逻辑

商品行与发货履约单的对应逻辑建议如下：

1. 电商系统完成订单主单创建
2. 电商系统遍历订单商品行，识别每个商品行的履约归属条件
3. 根据履约归属条件给商品行分组，形成 `shipment_group_no`
4. 每个履约组生成一张发货履约单
5. 每张发货履约单绑定唯一 `fulfillment_mode`
6. 每个商品行只归属到对应的一个履约组和一张发货履约单

### 6.7 映射校验规则

| 校验项       | 规则                                      |
| --------- | --------------------------------------- |
| 商品行唯一归属校验 | 同一个 `order_line_no` 不能重复出现在两张发货履约单中     |
| 履约模式一致性校验 | 同一张发货履约单下所有商品行的 `fulfillment_mode` 必须一致 |
| 数量完整性校验   | 发货履约单上商品行的数量必须等于原订单行数量，不支持拆分数量          |
| 汇总完整性校验   | 多张发货履约单下的商品行集合并后，应完整覆盖原订单商品行集合          |

## 7. 履约模式规则

### 7.1 履约模式定义

| 模式        | 说明       | 典型节点                    |
| --------- | -------- | ----------------------- |
| `INSTANT` | 即时配送履约模式 | 待接单、已接单、已取货、配送中、已送达     |
| `EXPRESS` | 快递配送履约模式 | 已打包、已出库、已揽收、运输中、派送中、已签收 |

### 7.2 模式适用规则

| 规则            | 说明                        |
| ------------- | ------------------------- |
| 模式归属于发货履约单    | 不归属于订单主单                  |
| 不同模式必须拆成不同履约单 | 即时配送与快递配送不能放在同一张发货履约单中    |
| 物流能力按模式解释     | 即时配送以轨迹查询为主，快递配送同时支持轨迹与面单 |

## 8. 状态与回调聚合规则

### 8.1 WMS 回调主键

WMS 回调应以 `shipment_order_id` 作为执行主键，同时返回以下关联信息：

- `parent_order_id`
- `shipment_order_id`
- `fulfillment_mode`
- `order_line_refs`
- `package_ids`

### 8.2 回调规则

| 回调类型     | 主键                  | 必带字段                                                     |
| -------- | ------------------- | -------------------------------------------------------- |
| 发货履约状态回调 | `shipment_order_id` | `parent_order_id`、`fulfillment_mode`                     |
| 包裹状态回调   | `package_id`        | `shipment_order_id`、`parent_order_id`、`fulfillment_mode` |
| 订单异常回调   | `shipment_order_id` | `parent_order_id`、`fulfillment_mode`、`order_line_refs`   |
| 单据流水回调   | `shipment_order_id` | `parent_order_id`、`fulfillment_mode`                     |

### 8.3 上游订单汇总规则

WMS 只负责回调发货履约单级状态，上游电商系统负责基于多个发货履约单汇总订单主单状态。

建议汇总逻辑如下：

| 订单主单汇总状态 | 建议规则                      |
| -------- | ------------------------- |
| 待履约      | 所有发货履约单都未进入正式执行           |
| 履约中      | 任一发货履约单进入执行中，且仍存在未完成履约单   |
| 部分完成     | 部分发货履约单完成，部分仍在执行或异常       |
| 已完成      | 所有发货履约单均完成                |
| 已异常      | 任一关键发货履约单失败，且订单主单无法继续正常完成 |

## 9. 责任边界

### 9.1 第三方电商系统职责

- 维护订单主单与商品行结构
- 在订单源头确定商品行归属的履约分组
- 为每张发货履约单明确 `fulfillment_mode`
- 调用 WMS 创建、确认、查询发货履约单
- 基于多个发货履约单状态汇总订单主单状态

### 9.2 WMS 职责

- 接收发货履约单并执行拣货、出库、包裹、物流、异常与回调
- 校验商品行归属是否唯一、数量是否完整
- 不负责猜测履约模式
- 不负责在无归属信息时自动决定拆单结构
