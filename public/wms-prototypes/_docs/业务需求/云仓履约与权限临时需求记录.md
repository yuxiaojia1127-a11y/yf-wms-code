# 云仓履约与权限临时需求记录

> 文档用途：沉淀云仓场景下的权限、履约拆分、运输要求与 OMS/WMS 对接临时需求，作为后续 PRD 与接口设计输入。
> 更新时间：2026-05-14
> 文档状态：临时记录，待评审收口

## 1. 需求背景

当前 WMS 已明确按多货主云仓模式建设，自营业务与第三方卖家业务共用一套底层履约体系。

现阶段存在两类典型业务差异：

| 业务场景    | 当前特征                           | 对 WMS 的影响                   |
| ------- | ------------------------------ | --------------------------- |
| 自营超市系统  | 一张订单仅支持一个前置仓发货，不需要分仓           | 可沿用单仓履约模型，但底层仍需兼容统一云仓能力     |
| 第三方卖家云仓 | 一张订单的商品可能分布在不同仓库，可能需要分仓履约、集货发货 | 需要支持一张上游订单拆成多个履约单、多个包裹、多个运单 |

因此，本期必须提前统一以下口径：

1. 作业人员权限按什么维度管控。
2. OMS 应如何向 WMS 下单，是否要明确运输要求与时效服务。
3. WMS 是否必须完全按 OMS 指定的配送模式执行，还是按规则校验后执行。
4. 门店、多仓、网络库存可售、分仓履约之间如何协同。

## 2. 本次临时需求范围

| 模块   | 本次关注点                   |
| ---- | ----------------------- |
| 权限模型 | 仓库、货主、履约店铺、岗位权限、作业类型权限  |
| 订单模型 | 上游订单、WMS 履约单、包裹、运单的层级关系 |
| 履约策略 | 单仓履约、分仓履约、集货/拆包、网络库存可售  |
| 配送规则 | 即时配送、快递物流、时效服务、规则校验     |
| 外部对接 | OMS 下单字段、运输要求传入、履约结果回传  |

## 3. 核心业务口径建议

### 3.1 权限管控维度

仓库作业人员权限建议按“组织维度 + 作业维度”双层设计：

| 权限维度   | 建议口径 | 说明                          |
| ------ | ---- | --------------------------- |
| 仓库权限   | 必选   | 限定用户可进入哪些实体仓、作业区         |
| 货主权限   | 必选   | 限定用户只能处理被授权货主的数据和作业单据       |
| 履约店铺权限 | 必选   | 满足自营业务按店铺管理、独立揽货员按店铺分权的诉求   |
| 作业类型权限 | 必选   | 区分收货、上架、拣货、复核、打包、出库、异常处理等能力 |
| 操作级权限  | 建议支持 | 区分查看、执行、强制完成、取消、异常处理、导出     |

补充说明：

1. 自营业务下，履约店铺不是货主，但应作为权限分配维度。
2. 第三方卖家场景下，货主隔离必须强于岗位隔离，避免跨货主误操作。
3. 若存在独立揽货员，应支持“只可查看/执行指定店铺 + 指定仓库 + 指定作业类型”的组合权限。

### 3.2 订单与履约对象层级

云仓场景建议拆分四层对象，避免把“订单”“包裹”“运单”混为一体：

| 对象   | 定义                        | 是否允许一对多 |
| ---- | ------------------------- | ------- |
| 上游订单 | OMS/电商系统下发给 WMS 的原始交易履约请求 | 1       |
| 履约子单 | WMS 根据仓库库存、规则、配送模式拆分出的执行单 | 1:N     |
| 包裹   | 打包后的物理包裹，承载实际出库商品         | 1:N     |
| 运单   | 对应承运商/即时配送平台生成的运输单号       | 1:N     |

结论建议：

1. 自营超市场景可继续沿用“一张订单对应一个履约单”的简化能力。
2. 云仓通用能力必须支持“一张上游订单拆成多个履约子单、多个包裹、多个运单”。
3. 不同商品可能由不同仓履约，不同履约子单也可能对应不同配送模式。

### 3.3 是否从一开始区分即时配送和物流发货

建议：需要从订单进入 WMS 的一开始就明确“运输要求”，但不一定等同于最终执行结果。

建议区分两个概念：

| 概念     | 含义                                | 来源         |
| ------ | --------------------------------- | ---------- |
| 运输要求   | 上游 OMS 对订单期望的配送模式、时效服务、服务承诺       | OMS 下单时传入  |
| 最终履约模式 | WMS 结合仓库能力、规则配置、库存分布、地址范围后确认的执行模式 | WMS 规则引擎判定 |

建议规则：

1. OMS 下单时必须传入期望配送模式，例如即时配送、快递物流、门店自提。
2. OMS 下单时建议同步传入时效服务，例如当日达、次日达、标准快递。
3. WMS 不承诺无条件按 OMS 要求执行，而是先校验仓库能力、地址服务范围、承运能力、库存分布与配置规则。
4. 若 WMS 可满足，则按 OMS 要求执行；若不可满足，应返回“拒单 / 改配建议 / 部分履约结果 / 拆单结果”。

### 3.4 OMS 应如何向 WMS 下单

OMS 对 WMS 的下单模型建议采用“主订单 + 商品明细 + 运输要求 + 履约约束”的标准结构。

建议最少传入以下信息：

| 字段                       | 是否必填 | 说明                  |
| ------------------------ | ---- | ------------------- |
| `channel_id`             | 是    | 接入渠道标识              |
| `business_type`          | 是    | 自营 / 第三方卖家          |
| `owner_id`               | 是    | 货主标识                |
| `store_id`               | 条件必填 | 履约店铺；自营场景建议必传       |
| `external_order_no`      | 是    | 外部订单号               |
| `order_lines`            | 是    | 商品明细、数量、单位、批次/效期要求  |
| `receiver_info`          | 是    | 收货人、地址、联系方式         |
| `delivery_mode_required` | 是    | 期望配送模式：即时配送 / 快递    |
| `service_level`          | 建议必填 | 时效服务：小时达、当日达、次日达、标准 |
| `split_delivery_allowed` | 建议必填 | 是否允许分仓履约 / 拆多个包裹    |
| `preferred_warehouse_id` | 可选   | 优先仓库；仅表达偏好，不保证生效    |
| `remark`                 | 可选   | 订单备注、特殊履约要求         |

下单原则建议：

1. 自营超市订单可继续限制为单仓履约，`split_delivery_allowed = false`。
2. 第三方卖家云仓订单建议支持 `split_delivery_allowed = true`，允许 WMS 分仓履约。
3. 若 OMS 不允许拆分，但单仓库存不足，WMS 应返回不可履约或等待人工处理，不能静默拆单。

### 3.5 WMS 是否一定按照 OMS 的运输要求执行

建议口径：OMS 提的是“履约要求”，WMS 输出的是“履约确认结果”。

| 场景                    | 建议处理方式                       |
| --------------------- | ---------------------------- |
| OMS 要求即时配送，仓库与地址均满足   | WMS 按即时配送执行                  |
| OMS 要求即时配送，但仓库无即时配送能力 | WMS 拒绝接单或按规则返回改配建议           |
| OMS 要求快递，但命中门店小时达规则   | 若业务规则允许，可升级为即时配送；否则仍按快递      |
| 订单已被分仓，不同仓支持能力不同      | 允许不同履约子单采用不同配送模式，但需明确回传给 OMS |

因此，需要在 WMS 内增加规则配置能力：

1. 配送模式规则：按店铺、仓库、货主、区域、商品分类、SKU 设定即时/快递能力。
2. 时效服务规则：支持小时达、当日达、次日达等服务时效配置。
3. 降级/升级规则：是否允许从即时降级为快递，或从快递升级为即时。
4. 失败策略：无法满足要求时，是拒单、部分履约还是转人工。

### 3.6 门店、多仓与网络库存可售

针对“门店可以有多个仓库，库存按总库存判断”的需求，建议口径如下：

| 口径      | 建议说明                          |
| ------- | ----------------------------- |
| 门店与仓库关系 | 一个履约店铺可绑定多个仓库                 |
| 可售库存判断  | 对外可按门店维度汇总多个仓库库存形成网络可售        |
| 实际履约分配  | 接单后再由 OMS/WMS 履约策略决定落到哪个仓或多个仓 |
| 单仓不足处理  | 当单仓库存不足但网络库存充足时，允许分仓履约        |
| 自营例外    | 自营超市现阶段仍可按单仓发货约束处理，不强制启用分仓    |

注意：

1. “网络库存可售”是销售口径，不等于现场作业口径。
2. 作业执行仍必须落到具体仓库、货位、包裹。
3. 若启用分仓履约，必须同步管理缺货、集货、包裹拆分、运单拆分和状态回传。

### 3.7 OMS 履约策略配置

建议 OMS 侧每个店铺都可配置履约策略，WMS 负责执行策略结果或配合策略落地。

建议支持的配置维度：

| 配置维度     | 是否建议支持 | 说明                  |
| -------- | ------ | ------------------- |
| 按店铺配置    | 是      | 最基础能力，决定店铺默认履约逻辑    |
| 按商品分类配置  | 建议支持   | 解决冷链、鲜食、大件等不同履约方式需求 |
| 按 SKU 配置 | 建议支持   | 适用于重点商品、特殊商品、管控商品   |
| 按区域配置    | 建议支持   | 不同配送区域支持不同仓和不同时效    |
| 按货主配置    | 是      | 第三方卖家之间服务能力和规则可能不同  |

建议职责边界：

1. OMS 负责生成履约偏好和约束条件。
2. WMS 负责基于库存、仓网、作业能力、物流能力执行或反馈无法执行原因。
3. 若 OMS 已完成明确分仓，WMS 应按指定仓执行；若 OMS 未分仓，则由 WMS 按规则分配。
