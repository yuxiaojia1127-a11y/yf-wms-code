# WMS原型设计说明

## 1. 文档目的

本目录用于沉淀基于最新 API 接口清单、`00WMS功能清单.md` 和流程图重新梳理后的 WMS 原型设计输入文档。

本轮原型设计不是对旧稿局部修补，而是按照最新系统边界重新建立一套新的原型文档体系，统一命名为 `WMS原型设计`，与旧版原型资料并行保留，便于后续评审对比。

## 3. 本次原型范围

本次只梳理 WMS 自身系统相关原型，不展开第三方电商系统自身页面和能力。

| 系统        | 本次处理方式 | 说明                                            |
| --------- | ------ | --------------------------------------------- |
| WMS\_WEB端 | 重点输出   | 承接开放平台运维、主数据、库存、单据、履约、物流协同、售后、调拨、异常、对账等后台管理能力 |
| WMS\_APP端 | 重点输出   | 承接仓内一线作业执行，重点覆盖收货、上架、备货、复核、出库、物流交接、退货、调拨、异常上报 |
| 第三方电商系统   | 不在本次范围 | 下单、履约仓选择、订单主单汇总、客服/运营后台等能力后续单独梳理              |

说明：

- `WMS_开放平台` 在功能清单中单独列示，但从原型设计角度以接口能力为主，不单独拆成独立系统。
- 需求文档侧将物流能力拆分为 `WMS_WEB_物流系统` 与 `WMS_APP_物流系统` 两部分，以便分别沉淀后台物流管理需求和现场物流作业需求。
- 原型设计侧不再保留独立的 `WMS_物流系统`，而是将上述两部分分别并入 `WMS_WEB端` 和 `WMS_APP端` 的物流协同模块处理。
- `WMS_WEB端` 侧承接运单、包裹、轨迹、回传、面单、物流对账等管理能力。
- `WMS_APP端` 侧承接出库后的物流选择、交接确认、运单回看和现场物流异常反馈。

## 4. 统一设计口径

| 口径     | 说明                                                        |
| ------ | --------------------------------------------------------- |
| 上游边界   | WMS 对上只对接统一的第三方电商系统，不拆电商运营后台、风控后台、客服后台等独立系统               |
| 订单模型   | 一个 `order_id` 可拆成多张 `shipment_order_id`，WMS 执行主对象是发货履约单   |
| 拆单规则   | 拆单按商品行拆分，不支持按数量拆分，一个 `order_line_no` 只能归属一张履约单            |
| 履约模式   | `fulfillment_mode` 归属发货履约单，标准值为 `INSTANT` 和 `EXPRESS`     |
| 店铺与仓库  | 店铺用于履约归属和服务关系，不是库存归属主体；库存归属围绕 `货主 + 仓库 + 货位 + 批次 + 状态` 建立 |
| 仓内术语   | 仓内执行统一使用 `备货`，不再使用旧稿中的 `揽货` 口径                            |
| APP 作业 | 仓库 APP 只支持在线实时作业，不做离线积压补传                                 |
| 物流边界   | 物流能力不单独拆系统，Web 管理物流协同，App 承接现场交接与物流反馈                     |
| 回调主体   | WMS 回调主体以发货履约单为主，上游负责订单主单状态汇总                             |

## 5. 原型设计原则

| 原则            | 说明                                |
| ------------- | --------------------------------- |
| 先系统后页面        | 先定义系统边界、信息架构、页面关系，再展开页面原型说明       |
| 只画 WMS 自身能力   | 不把第三方电商系统自身的订单、营销、用户侧页面混入 WMS 原型  |
| 页面来自功能清单      | 页面必须能回溯到最新功能清单和 API 分组，不再沿用旧版页面口径 |
| 先主链路后扩展能力     | 优先覆盖 P0/P1 模块，再补 P2/P3 的低频管理场景    |
| 先简易版 PRD 再做原型 | 每轮页面原型说明输出前，先产出对应模块的简易版 PRD 作为输入基线  |
| 强化状态与异常       | 每个页面必须体现正常态、空态、异常态、无权限态、操作成功/失败反馈 |
| 可交付           | 文档既能指导 UI 出图，也能让前端、测试、产品用于评审与实现   |

## 7. 页面文档分层

为避免不同文档承担重复信息，页面相关内容统一采用“页面清单轻量、页面原型说明详细”的两层表达方式：

| 层级 | 文件类型 | 固定表达重点 |
| ---- | ---- | ---- |
| 第一层 | 页面清单 | `页面目标 / 使用角色 / 页面入口 / 优先级 / 核心操作` |
| 第二层 | 页面原型说明 | 在页面清单基础上补充 `需求来源 / 页面布局 / 状态 / 异常 / 权限差异 / 交互细节` |

说明：

- 页面清单用于快速确认范围、优先级和页面职责，不承载过多设计细节。
- 页面原型说明用于支撑 UI、前端、测试和评审，负责补充来源、布局和交互设计。
- 信息架构文档只说明导航、模块关系、页面归属以及页面清单、页面原型说明的使用规则，不重复展开每页细节。

## 8. 本轮不展开内容

| 内容                   | 处理方式               |
| -------------------- | ------------------ |
| 第三方电商系统页面            | 不纳入本轮原型            |
| 电商运营后台页面             | 不纳入本轮原型            |
| 纯接口能力如 token 生成本身    | 以接口文档承接，不单独设计模拟调用页 |
| 与业务无直接关系的通用 UI 组件库规范 | 后续在可交互原型阶段补充       |

## 9. 评审重点

本轮新版原型文档建议重点评审以下问题：

1. 系统边界是否完全收敛到 WMS 自身能力。
2. `WMS_WEB端 / WMS_APP端` 的职责拆分是否清晰。
3. 物流能力并入 Web 和 App 后，模块归属是否合理。
4. 页面命名、对象主键、状态口径是否与最新 API 和流程图一致。
5. 是否存在需要反向回写 PRD 或功能清单的新增页面、状态或交互规则。
