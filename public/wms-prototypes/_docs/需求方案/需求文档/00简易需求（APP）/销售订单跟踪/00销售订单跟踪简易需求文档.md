# 仓库APP-销售订单跟踪简易需求文档

> 版本范围说明：本文档覆盖在仓库APP中以「销售订单」为单位，查看该订单 WMS 履约全链路的进度、各环节操作人与数据流（揽货指令下发 → 接单 → 揽货 → 打包复核 → 发货 → 配送 → 送达 → 完成）。本功能为**只读跟踪/查看**，不在本页执行接单、揽货、打包、发货等实际作业操作。WEB 端按相同信息架构另行输出。

## 2. 业务说明

一个销售订单在 WMS 内的履约过程会被拆解为多个环节、跨越多名操作人与多个库房：

- 电商系统支付完成后，WMS 按销售渠道绑定库房做 SKU 履约匹配，**一个订单可能拆分为多张揽货指令**（每个履约库房一张）。
- 每张揽货指令由揽货人员**接单**后**完成揽货**；当订单全部揽货指令完成揽货后，进入**打包复核**（订单级合单复核）。
- 打包完成后订单流转至待发货，由发货人员**发货**（即时配送走 Lalamove 等三方，或物流发货），随后进入**配送 → 送达 → 完成**。

「销售订单跟踪」以订单为中心，把全链路串起来，让管理人员在一个页面看清：订单有几张揽货指令、分别在哪些库房、履约什么商品；每个环节是谁操作的（接单人、揽货人、打包人、发货人）、各在什么时间完成；订单当前整体进度，以及是否存在缺货、退货、换货、退差价、配送异常等情况。

订单详情参考「打包复核」详情页的交互模式——通过**揽货指令切换（全部 / 揽货#N）**查看多张揽货指令的数据情况。

## 3. 功能描述

- 列表整体参考「发货管理」列表卡片结构（**不展示商品图片**）；详情整合「揽货详情 / 打包复核详情 / 发货详情」的内容，但**只展示各环节最终结果**（订单数量、实际揽货数量、打包复核数量、订单商品、实际揽货商品、退货/换货/退差价标记等），不还原扫码/步进等作业过程。
- 支持进入「销售订单跟踪」页面，查看可跟踪的销售订单列表。
- 支持按订单号 / 收货联系人 / 揽货指令任务ID 搜索订单。
- 支持按履约阶段页签筛选订单，顺序：全部 / 待接单 / 异常 / 揽货中 / 待打包 / 待发货 / 配送中 / 已完成；默认「全部」。「已完成」页签同时包含**已送达**与**已完成**两种订单。
- 各阶段页签（**全部、已完成除外**）右上角显示该阶段**待处理数量**角标，角标随当前配送类型筛选/搜索条件联动，与列表展示一致。
- 阶段页签横向可滚动，**「时间」排序固定在右侧不随页签滚动**。
- 支持按配送类型筛选：全部 / 即时配送 / 预约单 / 物流发货；**每个筛选项后显示该类型在当前阶段下的数量统计 (N)**（随阶段/搜索联动）。
- 支持按时间排序（下单时间升序 / 倒序），默认升序。
- 支持点击订单卡片或「跟踪详情」进入订单跟踪详情页。
- 订单跟踪详情页模块顺序：① 订单总览（含 6 步进度概览条）② 订单信息与收货人 ③ 订单商品（三数量对照 + 揽货指令切换）④ 打包复核记录 ⑤ 发货与配送记录 ⑥ 履约进度时间轴（置于详情最底部）。
- 订单商品区可在「全部 / 揽货#N」之间切换，查看每张揽货指令的库房、状态、接单/揽货人、商品明细与异常。
- **履约进度时间轴**承载数据流流水：每个节点展示「节点 + 操作人 + 操作时间 + 操作结果」，形成可追溯的履约记录。
- 全程**只读**：本页不提供接单、揽货、打包、发货、改址、扫码、步进等任何写操作入口。

## 4. 履约全链路阶段定义

订单跟踪以下列阶段为主线，整体进度取自订单级揽货单 `w_wms_picking_orders.status`、各时间戳，并结合 `w_wms_delivery_orders.delivery_status`。

| 阶段 | 阶段含义 | 主要数据来源 | 关键时间 |
| ---- | ---- | ---- | ---- |
| 已下单 / 已支付 | 电商支付完成，WMS 生成订单揽货单 | `picking_orders`（created_at）、`pay_orders` | 下单时间 / 付款时间 |
| 待接单 | 揽货指令已下发、尚无人接单 | `picking_depot_tasks`（picker_id 为空） | 指令生成时间 |
| 揽货中 | 揽货人员接单后开始拣货 | `picking_orders`（picking_at）、`depot_tasks`（picker、status 揽货中） | 接单 / 进入揽货中时间 |
| 待打包 | 各库房揽货指令完成揽货，订单全部到齐 | `depot_tasks`（status 已揽货）；`picking_orders`（picked_at） | 进入待打包时间 |
| 待发货 | 订单级合单复核并完成打包 | `picking_orders`（packer_id/name、packed_at、review_photos） | 完成打包时间 |
| 配送中 | 发货人员发货，三方/物流配送中 | `picking_orders`（shipped_at）、`delivery_orders`（creator_id、delivery_status=配送中） | 发货时间 |
| 已送达 | 配送已送达，用户尚未确认收货 | `delivery_orders`（delivery_status=已送达）、`delivery_order_tracks` | 送达时间 |
| 已完成 | 送达后用户确认收货，**或超过 1 天系统自动置为已完成** | `picking_orders`（received_at，status 6 已收货） | 收货 / 完成时间 |
| 异常 / 已取消 | 订单取消或环节异常（跨阶段标识） | 各表 status（缺货/退货/换货/退差价/配送异常/拦截/取消） | 异常发生时间 |

> 进度概览条（6 步）：**接单 → 揽货 → 打包 → 发货 → 送达 → 完成**。存在多张揽货指令时，揽货阶段细分进度按各 `depot_tasks` 完成情况聚合（如「揽货 2/3 已完成」）。
>
> 列表「已完成」页签归集「已送达 + 已完成」两类订单；卡片整体进度标签仍按订单真实状态分别显示「已送达 / 已完成」。

## 5. 角色与操作人映射

| 角色 | 含义 | 数据来源 | 展示位置 |
| ---- | ---- | ---- | ---- |
| 接单 / 揽货人 | 接单并完成该库房揽货指令的人员（通常同一人，揽货人接单） | `picking_depot_tasks.picker_id` / `picker_name`（**按揽货指令各自记录**） | 揽货指令卡 / 时间轴 |
| 打包人 | 完成订单级打包复核的人员 | `picking_orders.packer_id` / `packer_name` | 打包记录 / 时间轴 |
| 发货人 | 创建发货/配送单的人员 | `delivery_orders.creator_id` | 发货记录 / 时间轴 |
| 配送司机 | 三方配送骑手（即时配送） | `delivery_orders.driver_info` | 配送记录 |

> 接单人与揽货人当前共用 `picker` 字段，统一展示为「接单/揽货人」。若后续需要区分二者，需在 `picking_depot_tasks` 增加独立字段。

## 7. 履约进度时间轴（核心，置于详情最底部）

时间轴位于详情页最底部，按发生顺序展示各节点，每个节点统一结构：**节点名称 + 操作人 + 操作时间 + 结果/备注**。未到达的节点以灰态/虚线占位。时间轴承载订单全生命周期的数据流流水，是操作记录的追溯入口。

| 节点 | 操作人展示 | 时间 | 结果/备注示例 |
| ---- | ---- | ---- | ---- |
| 已下单 / 已支付 | 下单用户 | 下单时间 / 付款时间 | — |
| 揽货指令下发 | 系统 | 指令生成时间 | 共下发 2 张揽货指令 |
| 接单 | 接单/揽货人（按指令） | 接单时间 | 揽货#1 由 张三 接单 |
| 揽货中 / 已揽货 | 接单/揽货人（按指令） | 各指令完成时间 | 揽货#1 已完成揽货（含换货 1 项） |
| 待打包（全部揽货到齐） | 系统 | picked_at | 2 张揽货指令全部完成 |
| 已打包 | 打包人 | packed_at | 李四 完成打包复核 |
| 已发货 | 发货人 | shipped_at | 王五 发货（Lalamove） |
| 已送达 | 配送司机 | 送达时间 | 取自配送轨迹 / 状态 |
| 已完成 | 系统 / 用户 | received_at | 用户确认收货，或送达后超 1 天自动完成 |

> 异常节点（缺货/退货/换货/退差价/配送异常/订单拦截/取消）以橙色或红色高亮插入对应时间点，标注异常类型与发生时间。

## 8. 订单商品（整合揽货/打包/发货最终结果 + 揽货指令切换）

> 整块为详情页第 ③ 模块，承载于**单一卡片**内。整合「揽货详情、打包复核详情、发货详情」的商品信息，只展示各环节最终结果，不还原扫码/步进等作业过程。交互参考打包复核详情页，通过「全部 / 揽货#N」切换查看。

### 8.1 切换项

### 8.2 「全部」视图：订单商品三数量对照（最终结果）

以订单商品为行，横向对照下单、揽货、打包复核三个环节的最终数量结果，并标识异常。

| 字段名称 | 字段类型 | 示例 | 说明 |
| ---- | ---- | ---- | ---- |
| 商品图片 | 图片 | — | 辅助识别 |

| 商品规格 | 文本 | 礼盒装 ｜ 0.22KG | SKU 规格 |

| **实际揽货数量** | 数值 | 2 | 各揽货指令实际已揽数量按 SKU 汇总（含换货商品） |
| **打包复核数量** | 数值 | 2 | 打包出库数量（见 §10 取数口径） |

| 异常 | 缺货 / 退货 / 换货配对 / 退差价（见 §8.5） |

### 8.5 异常商品展示形态（参考揽货功能）

异常依据 `depot_task_skus`：`status`（3换货 / 4退货 / 6退差价）、`source_type`（1原订单 / 2换货商品）、`origin_id`（换货商品指向被换原商品行）。五种形态如下：

| 形态 | 标签 | 三数量表现 | 附加 |
| ---- | ---- | ---- | ---- |
| 正常 | 无（绿勾） | 订单 = 实揽 = 复核 | — |
| 缺货（部分） | 红「缺货」 | 实揽栏红橙 | 单行「缺货 N 件」（N = 订单 − 实揽） |
| 退货 | 红「退货」 | 实揽/复核红橙（多为 0） | 单行「退货 N 件」 |
| 换货 | 橙「换货」 | 原商品实揽/复核红橙（多为 0） | **换货配对块**（见下） |
| 退差价 | 橙「退差价」 | 订单 = 实揽 = 复核 | 仅标签 |

> 标签即表达异常类型，附加行只保留必要数量；不展示「库存不足」原因与「仅标记/待退款」状态，保持紧凑。退货/退差价本期仅做标记，退款状态待后续对接电商退款功能后再定。

**换货配对块（原商品 ↔ 实际商品）**：在原商品行下方缩进「╰→ 换货为」，展示实际换货商品（source_type=2、origin_id=原行）：商品图 / 名称 / 规格 / 条码 + **仅「实际揽货 / 打包复核」两数量**（换货商品非原始下单，**不展示「订单数量」**）。一个原商品可挂多条换货商品。换货商品的实际揽货计入订单「实际揽货」「打包复核」汇总，原商品对应数量为 0。

### 10.2 待评估 / 可能新增项

1. **接单人与揽货人是否区分**：当前共用 `picker`，合并展示为「接单/揽货人」。如需独立展示，需在 `picking_depot_tasks` 增字段。
2. **履约时间轴聚合方式**：实时按各表状态时间戳聚合，或新建跟踪流水表落地。建议先用实时聚合（无需建表）。
3. **整体进度细分口径**：揽货阶段多指令进度（如 2/3）在查询层聚合，无需新增字段。
4. **退货/退差价退款状态**：本期仅标记，后续对接电商退款功能后再定退款状态展示。
5. **查看权限**：跟踪页含成本/操作人信息，需按角色控制可见范围。

## 11. 关键业务规则

1. **订单级聚合**：跟踪以销售订单为单位，向下聚合多张揽货指令、打包记录与发货记录。
2. **只读不作业**：本页不提供任何写操作；如需操作请前往对应作业页面。
3. **多揽货指令切换**：订单商品区支持「全部 / 揽货#N」切换查看。
4. **三数量对照**：订单数量、实际揽货数量、打包复核数量并列对照，差异自动高亮。
5. **异常最终结果**：缺货 / 退货 / 换货 / 退差价 / 配送异常在卡片、商品行、时间轴统一高亮；换货以「原商品 ↔ 实际商品」配对展示。
6. **列表对齐发货管理**：列表卡片结构参考发货管理列表，不展示商品图片。
7. **只看最终结果**：详情整合揽货/打包/发货详情内容，只呈现各环节最终结果，不还原作业过程。
8. **数据以库表为准**：所有展示字段对齐 `wms` 库真实表，未落库字段按 §10.2 标注。
9. **WEB 端对齐**：WEB 端按相同信息架构（总览 + 订单商品 + 打包/发货记录 + 履约进度时间轴）实现。
