name: annotatable-requirements-editor
description: 将需求文档转换为基于代码持久化的、可编辑的页面需求标注系统。适用于以下场景：用户希望根据 PRD 初始化页面需求标注；更新已有标注内容；将只读标注升级为可编辑标注；在标注前先优化需求文档；以及确保页面内编辑后的需求内容能够真实写回代码中的需求文件并作为部署时的正式来源。
---

# 目标

将需求文档与页面 UI 转换为一套**单一事实来源**的需求标注系统，使其同时满足以下两个目标：

1. **研发可读**  
   研发人员可以直接通过页面角标与需求浮窗，完整理解模块需求、业务逻辑、前置条件、边界情况、异常流程与补充说明，而不需要重新阅读原始 PRD。

2. **研发可维护**  
   研发人员可以直接在页面浮窗中编辑需求内容，并将编辑结果写回代码中的需求文档文件。保存后的需求文档即为部署时使用的正式需求来源。

需求文档页面与页面标注系统必须读取**同一份代码内需求数据**。

---

# 核心原则

## 1. 一个模块只允许一个角标、一个需求编号
同一组件或紧密关联的模块上，禁止出现多个需求角标。

## 2. 零信息丢失
在做模块聚合时，必须完整保留原始需求中的：
- 业务逻辑
- 前置条件
- 异常流程
- 边界情况
- 补充说明

禁止为了“简化表达”而删减细节、弱化约束或遗漏条件。

## 3. 必须使用代码内真实持久化
编辑结果必须写回代码仓库内的需求文件。  
禁止使用前端 state、内存变量或临时缓存伪装为“已保存”。

## 4. 同源渲染
需求文档页面与页面中的标注浮窗，必须来自同一份需求源数据。

## 5. 更新时最小破坏
当处理已有标注系统时，应优先保留：
- 模块聚合方式
- 需求编号
- 锚点定位规则
- 渲染结构

除非用户明确要求重构，否则只更新目标模块或目标交互层。

# 首先做任务判定

开始执行前，必须先判断当前任务属于哪一类。

## 路径 A：初始化标注
以下情况使用初始化流程：
- 用户提供了新的 PRD 或新页面
- 当前页面还没有需求角标 / 需求浮窗系统
- 用户希望从零开始建立标注系统

## 路径 B：标注内容更新
以下情况使用更新流程：
- 页面已经存在需求标注
- 用户希望对已有标注内容做增量修改
- 用户希望把只读标注升级为可编辑标注
- 用户希望在保留原有模块映射结构的前提下，补充编辑和持久化能力

## 如果意图不明确
必须先询问用户，不得自行猜测：

> 请问您是需要执行【Workflow A: 初始化标注】（针对新页面/新文档），还是执行【Workflow B: 标注内容更新】（针对已有标注的增量修改或改造成可编辑式）？

# 预处理规则：先询问是否需要优化需求文档

收到需求文档后，第一步不是直接标注，而是先询问用户是否需要优化需求文档。

## 如果用户需要优化
必须先完成以下动作，再进入实现阶段：
1. 深度解析 PRD
2. 查漏补缺
3. 补充边界情况与失败场景
4. 修复逻辑漏洞、冲突与歧义
5. 把修改了哪些内容明确告知用户
6. 新增或更新“需求文档页面”，以说明手册形式完整展示需求文档
7. 将所有需求点按功能模块聚合后，挂载到 UI 标注系统中

## 如果用户不需要优化
则按以下流程执行：
1. 深度解析 PRD
2. 按功能点拆分与聚合需求
3. 新增或更新“需求文档页面”，以说明手册形式完整展示需求文档
4. 将所有需求点按功能模块挂载到 UI 标注系统中

无论是否优化，需求文档页面与页面标注系统都必须来自同一份代码内需求源。

---

# 必须遵循的执行顺序

执行时必须严格按以下顺序进行：

1. 判定任务属于初始化还是更新
2. 识别页面模块边界
3. 按模块聚合需求
4. 生成或更新“角标 - 模块”映射关系
5. 实现或更新需求浮窗
6. 如果要求可编辑，则补全编辑态与持久化能力
7. 自检交互、样式、内容完整性与写回结果

---

# Workflow A：初始化标注

适用于新页面或尚未建立需求标注系统的页面。

## 步骤 1：识别模块边界
标注前必须先按功能区域划分模块。

示例：
- 行内操作中的编辑、删除、查看、权限控制 -> 聚合为一个“操作模块”
- 所有筛选输入框、下拉框、查询按钮、重置按钮 -> 聚合为一个“筛选模块”
- Tab 切换逻辑 -> 聚合为一个“Tab 模块”

## 步骤 2：按模块聚合需求
每个模块应形成一条完整的需求记录。

每条记录至少包含：
- 模块名称
- 显示样式
- 交互逻辑
- 业务规则
- 前置条件
- 异常流程
- 备注
- 原始 Markdown 内容

## 步骤 3：生成初始化产物
初始化完成后，至少必须产出：
- 页面模块与需求编号的映射关系
- 每个模块对应的浮窗内容
- 页面可直接渲染的需求数据文件
- 代码内的初始需求文档

## 步骤 4：与页面绑定
页面必须直接根据代码内需求文档渲染角标与浮窗，  
不能只依赖每次运行时重新解析外部 PRD。

---

# Workflow B：标注内容更新

适用于对已有标注系统做内容更新，或将只读系统升级为可编辑系统。

## 更新规则
- 保持原有模块聚合方式不变
- 保持一个模块只对应一个需求编号
- 默认只更新目标模块，不影响其他模块
- 不得破坏编号、结构、定位规则和渲染逻辑
- 优先采用最小破坏式改造

## 可编辑能力
每个需求浮窗必须支持：
- 查看态
- 编辑态

编辑态至少允许编辑：
- 模块名称
- 需求描述
- 补充说明
- 该模块所属的结构化内容字段

## 保存行为
点击保存后，系统必须：
- 通过 `pageId + moduleId` 或 `moduleKey` 精确定位目标模块
- 只更新目标模块
- 禁止整份文档粗暴替换
- 保持其他模块内容不变
- 返回最新保存结果与更新时间
- 保存失败时保留当前编辑内容
- 明确提示失败原因

## 部署一致性
保存后的需求文档必须是项目代码的一部分，且部署后页面直接使用这份最新内容。  
禁止出现“UI 提示保存成功，但部署仍读旧文档”的伪持久化情况。

# 需求文档的标准存储方式

需求文档必须存在于代码仓库中，而不是只依赖外部上传的 `prd.md`。

## 推荐路径
优先使用结构化存储：
- `/src/requirements/annotated-prd.json`
- `/src/requirements/annotated-prd.yaml`

仅在业务明确依赖 Markdown 时使用：
- `/src/requirements/annotated-prd.md`

## 推荐数据结构
推荐使用“结构化字段 + rawMarkdown”双存储模式，以兼顾可编辑性和高保真展示。

```json
{
  "pageId": "user-list",
  "pageTitle": "用户列表页",
  "modules": [
    {
      "id": 1,
      "moduleKey": "filter-panel",
      "moduleName": "筛选模块",
      "anchor": {
        "selector": "[data-module='filter-panel']",
        "position": "top-right"
      },
      "content": {
        "displayStyle": "包含输入框、下拉框、查询/重置按钮",
        "interaction": [
          "查询按钮触发列表刷新",
          "重置按钮清空全部筛选项"
        ],
        "businessRules": [
          "默认按最近更新时间倒序",
          "状态筛选支持多选"
        ],
        "preconditions": [],
        "exceptionFlows": [],
        "notes": [
          "为空时展示全部数据"
        ],
        "rawMarkdown": "### 显示样式\n...\n### 交互与排序\n..."
      },
      "updatedAt": "2026-04-13T14:00:00+08:00"
    }
  ]
}
```

## 每个模块的必备字段
- `id`
- `moduleKey`
- `moduleName`
- `anchor`
- `content.displayStyle`
- `content.interaction`
- `content.businessRules`
- `content.preconditions`
- `content.exceptionFlows`
- `content.notes`
- `content.rawMarkdown`
- `updatedAt`

## 写回规则
点击保存后，系统必须：
- 根据 `pageId + moduleId` 或 `moduleKey` 精准定位目标模块
- 仅覆盖目标模块内容
- 保留原有编号、模块归属与锚点规则
- 刷新 `updatedAt`
- 若存在版本号，也需同步刷新版本元数据

---

# 需求文档页面要求

项目中必须存在一个“需求文档页面”，用于以说明手册形式完整展示需求内容。

## 页面要求
- 左侧必须有目录 / 导航
- 同一个大功能下的页面要归在同一分类中
- 若已有需求文档页面，应优先在原页面上更新，而不是重复新增
- 所有需求点必须以功能聚合方式进行展示
- 页面内容必须与页面标注系统来自同一份需求源数据

---

# 需求浮窗规范

需求浮窗必须同时满足“完整展示需求”和“支持在线维护需求”两种诉求。

## 顶部标题栏
顶部需展示：
- 模块标题
- 与页面指标一致风格的需求编号
- 标题下方的分隔线
- 右上角操作按钮

### 查看态显示
- `编辑`
- `X`

### 编辑态显示
- `保存`
- `取消`
- `X`

规则：
- `X` 仅表示关闭浮窗
- `保存` / `取消` 仅表示编辑状态操作，不等同于关闭

---

# 查看态渲染规则

查看态必须高保真渲染 Markdown。

必须保留：
- 段落间距
- 加粗与斜体
- 多级无序 / 有序列表层级
- 引用块结构
- 绿色、红色等状态表达的语义提示（必要时可加彩色圆点）

建议排版：
- `line-height: 1.6`
- `margin-bottom: 12px`

---

# 编辑态结构

优先使用：**结构化字段 + rawMarkdown 双存储**

编辑态可包含以下区域：
- 模块名称
- 需求摘要
- 显示样式
- 交互与排序
- 业务定义
- 前置条件
- 异常流程
- 备注
- 原始 Markdown 编辑区

规则：
- 页面渲染可以来自结构化字段，也可以来自 `rawMarkdown`
- 保存时必须同步更新结构化字段与 `rawMarkdown`
- 若两者不一致，以本次最终保存内容为准

---

# 保存前校验

以下情况禁止保存：
- 模块名称为空
- 需求描述为空
- 整块内容被清空
- Markdown 非法且会破坏必需结构
- 缺少必填结构化字段

若保存失败：
- 必须保留当前编辑内容
- 明确提示失败原因
- 不能自动退回旧数据覆盖用户当前编辑结果

---

# 浮窗内容最少必须覆盖的章节

无论查看态还是编辑态，浮窗内都必须按“小标题 + 内容”的方式组织，至少包含：
- 显示样式
- 交互与排序
- 业务定义
- 前置条件
- 异常流程
- 备注

如果原始 PRD 还有更多章节信息，也必须完整纳入。

# 角标与布局规则

## 非侵入式要求
- 使用 `position: absolute`
- 不得影响原页面 DOM 的宽高、布局和间距

## 角标定位
- 默认放在目标模块右上角附近
- 默认偏移：`top: -8px; right: -4px;`

## 层级要求
- 角标不能被页面元素遮挡
- 若目标组件存在 `overflow: hidden`，则应把角标挂载到 `body` 并基于全局坐标定位
- 浮窗层级固定为 `z-index: 9999`

## 边界处理
- 浮窗默认出现在角标左下方向，间距 8px
- 靠近视口边缘时必须自动翻转位置，防止超出可视区域

---

# 视觉样式规则

## 角标样式
必须严格使用：
- `display: inline-block; vertical-align: top;`
- 背景：`rgb(250, 173, 20)`
- 文字颜色：白色
- 字号：`10px`
- 字重：粗体
- 行高：`14px`
- `padding: 0px 4px;`
- `border-radius: 2px;`
- 无边框
- `cursor: pointer;`
- 编号范围：`1-999`

## 浮窗样式
- 背景：`#0eefef`
- `border-radius: 4px`
- 宽度：`450px`
- 轻微阴影
- 右上角关闭按钮

---

# 交互规则

## 唯一性
- 同一个需求编号的浮窗只能同时打开一个
- 不同需求编号的浮窗允许同时打开多个

## 事件隔离
点击以下区域时必须阻止事件冒泡，且不能触发底层页面事件：
- 浮窗内容区
- 输入框
- 滚动区域
- 按钮区域
- 拖拽区域

## 拖拽
- 整个浮窗必须支持鼠标拖拽
- 拖拽时不能触发底层页面点击
- 编辑态下的输入行为不能与拖拽产生冲突

## 关闭行为
- 浮窗只能通过 `X` 关闭
- 点击外部区域不得自动关闭，除非用户明确要求该行为

## 编辑交互
- 点击 `编辑` -> 进入编辑态
- 点击 `保存` -> 执行真实持久化
- 点击 `取消` -> 放弃本次修改，恢复到最近一次保存状态
- 保存中必须显示 loading，防止重复提交
- 保存成功后切回查看态，并展示最新更新时间
- 保存失败时必须提示原因，并保留当前编辑内容

# 服务端保存规则

服务端必须执行以下步骤：
1. 读取代码仓库中的需求文件
2. 根据 `pageId + moduleId` 或 `moduleKey` 定位模块
3. 仅更新目标模块
4. 更新 `updatedAt`，如有版本号也同步更新
5. 将最新结果写回代码文件
6. 返回更新后的模块内容

示例：

```ts
import fs from "fs";
import path from "path";

const filePath = path.resolve(process.cwd(), "src/requirements/annotated-prd.json");

export async function saveRequirement(payload) {
  const json = JSON.parse(fs.readFileSync(filePath, "utf-8"));

  const module = json.modules.find((m) => m.id === payload.moduleId);

  if (!module) {
    throw new Error("requirement module not found");
  }

  module.content = payload.content;
  module.updatedAt = new Date().toISOString();

  fs.writeFileSync(filePath, JSON.stringify(json, null, 2), "utf-8");

  return module;
}
```

# 并发与冲突处理

如果存在多人协作编辑，建议增加乐观锁机制：
- 使用 `updatedAt` 或 `version`
- 若客户端版本落后于服务端当前版本，则拒绝覆盖
- 提示用户重新加载最新内容后再编辑
- 禁止静默覆盖他人已保存的修改

# 执行强约束

执行时必须遵守以下约束：
1. 一个组件或模块只允许一个角标
2. 所有需求细节必须完整保留
3. 浮窗必须支持查看、编辑、拖拽、事件隔离、保存与关闭

当执行此 skill 时，建议按以下结构输出结果：

## 1. 任务分类

- Workflow A：初始化标注

按通过 / 不通过说明：

# 完成前的自检清单

结束前必须确认以下项目：

## 指令对齐
- 当前执行的是初始化还是更新，是否判断正确

## 聚合正确性
- 每个模块是否只有一个角标
- 相关需求点是否已正确聚合

## 内容完整性
- 业务逻辑、前置条件、异常流程、备注是否完整保留

## 交互正确性
