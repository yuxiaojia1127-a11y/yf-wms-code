# PRD Functional Annotator

## Overview

将 `prd.md`、页面截图、设计稿、前端实现内容，转换为**可供研发直接阅读的结构化标注说明**。

本技能的核心规则只有两层：

1. **按菜单拆文件**：不同菜单分别输出到不同标注文件。
2. **按业务功能分组标注**：同一菜单内，不按视觉组件聚合，而按业务目标拆分功能组。

标注结果必须足够完整，研发人员仅通过浮窗说明和菜单标注文件，就应能理解需求主体、交互规则、边界条件和异常处理，而无需回看原始 PRD。

## Workflow Decision

先做任务判定，再执行对应流程。

### Step 1：判断任务范围

先判断输入涉及的是：

- **单个菜单**：进入该菜单的初始化或更新流程。
- **多个菜单**：必须先按菜单拆分，再为每个菜单分别执行流程。

### Step 2：判断任务类型

- **初始化标注**：当前菜单还没有标注文件，或用户要求首次建立完整标注。
- **增量更新**：当前菜单已经有标注文件，用户要求根据修改后的 PRD / 页面 / 设计稿更新标注。

### Step 3：判断标注粒度

在单个菜单内部，**禁止默认按组件聚合**。

始终先判断业务功能边界：

- 同一业务目标 → 合并为一个功能组
- 不同业务目标 → 拆分为不同功能组

组件、卡片、表格、表单、弹窗，只是功能的承载容器，不是默认的聚合边界。

## Core Rules

### 1. 菜单级文件拆分

- 不同菜单必须输出到不同文件。
- 一个文件只允许承载一个菜单的标注内容。
- 若输入覆盖多个菜单，先拆菜单，再分别产出文件。
- 文件名必须能体现菜单语义，禁止无语义命名。

推荐命名：

- `用户管理.md`
- `角色权限.md`
- `订单管理.md`

如需排序，可加前缀：

- `01-用户管理.md`
- `02-角色权限.md`

### 2. 功能分组优先于组件分组

同一菜单内，按“用户要完成什么业务动作”分组，而不是按页面区域或组件盒子分组。

优先识别以下常见功能组：

- 查询 / 筛选
- 列表浏览
- 详情查看
- 新增
- 编辑
- 删除
- 启用 / 停用 / 状态变更
- 批量操作
- 审批 / 发布
- 导入 / 导出
- 权限配置
- 关联配置
- 日志 / 操作记录

判定标准：

- **同一业务目标**，即使跨多个控件，也应合并为一个功能组。
- **不同业务目标**，即使位于同一组件内，也必须拆分。

### 3. 组件仅作为锚点，不作为聚合依据

标注角标挂载到最能代表该业务目标的位置，但挂载位置不决定分组方式。

例如：

- 表格上方同时有“导出”“新增”“批量删除”按钮时，不能因为它们位于同一工具栏就聚合为一个编号。
- 行内“查看”“编辑”“删除”“重置密码”若业务目标不同，应分别标注，或明确拆成多个功能组。

### 4. 一个功能组对应一个编号和一段完整说明

- 一个功能组 = 一个需求编号 = 一个浮窗说明块
- 一个功能组可以覆盖多个页面元素
- 一个页面区域可以出现多个编号，只要它们分别对应不同业务目标

禁止以下错误：

- 因为元素相邻就强行合并
- 因为同属一个组件就只保留一个编号
- 将多个独立业务动作塞进同一个模糊标题里，例如“用户操作”“表格功能”

### 5. 输出内容必须可替代 PRD 阅读

每个功能组的说明，必须完整覆盖：

- 业务目标
- 触发入口
- 功能规则
- 交互反馈
- 边界条件
- 异常处理
- 与其他模块的依赖关系（如有）

禁止只写“支持新增/编辑/删除”这类空泛语句。

## Workflow A：初始化标注

当菜单首次建立标注时，严格按以下步骤执行。

### A1. 识别菜单边界

从输入材料中识别菜单列表，并建立菜单映射。

识别依据可以来自：

- PRD 中的菜单章节
- 页面标题 / 面包屑
- 路由名称
- 设计稿标题
- 页面导航结构

若一个页面同时包含多个菜单内容，必须先拆解归属，再分别输出。

### A2. 为每个菜单创建独立标注文件

每个菜单建立一个独立文件。推荐结构如下：

```md
# 菜单名称

## 菜单概述
[本菜单承载的业务目标、角色、适用场景]

## 功能索引
- [UM-01] 查询筛选
- [UM-02] 列表查看
- [UM-03] 新增用户
...

## 功能标注明细
[逐个功能组展开]
```

### A3. 菜单内先做业务功能分组

开始标注前，必须先完成菜单内部的业务功能拆分。

拆分原则：

1. 先识别用户目标，而不是视觉区域。
2. 再把服务于同一目标的控件、状态、流程、校验、反馈合并为一个功能组。
3. 对于复合操作区，拆出独立功能组。

示例：

**错误分法**

- 把“搜索框 + 状态筛选 + 导出按钮 + 新增按钮”整块作为“顶部工具栏”一个编号。

**正确分法**

- 查询筛选
- 导出数据
- 新增记录

### A4. 生成功能编号

编号必须在单个菜单内唯一、稳定、可追踪。

推荐优先使用“菜单缩写 + 顺序号”格式：

- `UM-01` 用户管理 / 查询筛选
- `UM-02` 用户管理 / 列表查看
- `UM-03` 用户管理 / 新增用户

若用户已有既定编号体系，优先沿用用户体系，但仍需满足：

- 同一菜单内唯一
- 更新时尽量稳定
- 不因描述顺序轻易重排

### A5. 为每个功能组选择代表性锚点

角标应挂载在最能代表业务目标的位置：

- 查询筛选：筛选区右上角或标题附近
- 列表浏览：表格标题区
- 行内操作：操作列标题处；若必须强调具体按钮，可挂首个典型按钮附近
- 新增：新增按钮附近
- 导入 / 导出：各自按钮附近
- 弹窗表单：弹窗标题右上角
- 详情模块：模块标题处

要求：

- 角标不遮挡关键文本和交互控件
- 同一区域允许多个角标并存，但必须对应不同功能组
- 锚点只是入口，不得因此改变分组边界

### A6. 撰写功能组说明

每个功能组都必须使用以下模板。

```md
### [UM-03] 新增用户

**业务目标**
支持管理员创建新用户，并配置基础信息与角色权限。

**触发入口**
点击页面右上角“新增用户”按钮。

**功能规则**
1. 打开新增用户弹窗。
2. 表单包含：用户名、姓名、手机号、邮箱、角色、状态。
3. 用户名必填且全局唯一。
4. 手机号校验格式。
5. 角色为必选。
6. 点击保存后提交创建请求。
7. 创建成功后关闭弹窗并刷新列表。

**交互反馈**
- 保存中按钮置灰并显示 loading。
- 保存成功 toast 提示“创建成功”。
- 校验失败时在字段下方展示错误信息。

**边界与异常**
- 用户名重复时禁止提交。
- 接口失败时保留用户已输入内容并允许重试。
- 无创建权限时隐藏或禁用新增入口。

**依赖与备注**
- 角色列表来源于角色管理配置。
```

撰写时必须做到：

- 不遗漏关键字段、状态、条件、前后置动作。
- 不照抄 PRD 的模糊表述，要补足研发落地需要的细节。
- 不输出与当前功能组无关的冗余内容。

### A7. 生成菜单级功能索引

在菜单文件顶部维护功能索引，方便研发按编号跳转。

示例：

```md
## 功能索引
- [UM-01] 查询筛选
- [UM-02] 列表查看
- [UM-03] 新增用户
- [UM-04] 编辑用户
- [UM-05] 删除用户
```

## Workflow B：增量更新

当用户提供修改后的 PRD、页面实现、设计稿，要求更新标注时，按以下流程执行。

### B1. 先定位菜单文件

先判断变更属于哪个菜单：

- 新菜单 → 新建独立文件
- 既有菜单 → 只修改该菜单对应文件
- 禁止跨菜单混写

### B2. 再判断功能组归属

对每项变更，必须判断属于：

- 新增功能组
- 既有功能组补充
- 既有功能组拆分
- 既有功能组删除
- 既有功能组重命名或重组

### B3. 保持编号稳定

增量更新时，优先保留已有编号。

只有在以下情况下才新建编号：

- 新增独立业务目标
- 旧功能组被拆分成多个独立业务目标
- 原编号语义已不再成立，且保留会误导研发

避免因为文本润色或顺序调整而整体重排编号。

### B4. 发现“组件式旧标注”时主动拆分

若旧标注是按组件聚合的，而新规则要求按功能分组，则必须拆分。

示例：

旧标注：

- `[UM-08] 用户操作`：包含查看、编辑、删除、重置密码

新规则下应拆分为：

- `[UM-08] 查看用户`
- `[UM-09] 编辑用户`
- `[UM-10] 删除用户`
- `[UM-11] 重置密码`

### B5. 删除与失效处理

如果某功能已下线或不再属于该菜单：

- 从功能索引中移除
- 在正文中删除对应说明，或按用户要求保留“已废弃”记录
- 若用户未要求保留历史，默认输出当前有效状态

## Bidirectional Writing

### 1. 反向写回原则

标注结果不仅用于页面浮窗，也要能反向写回 PRD 或菜单说明文件。

写回时遵守：

- 每个菜单维护独立的标注文件
- 每个功能组写入独立编号、功能名称和完整说明
- 可以从原始“页面模块视角”重组为“功能分组视角”
- 允许优化原文组织，但不得丢失原始需求信息

### 2. 逻辑同步原则

必须确保以下三者语义一致：

- 页面角标
- 菜单级标注文件
- PRD 中对应需求描述

禁止出现：

- 页面是“导出数据”，文件里写成“顶部工具栏”
- 页面拆成三个功能组，PRD 回写仍只保留一个模糊编号

### 3. 写回格式建议

若需要回写到 `prd.md`，优先使用“菜单 -> 功能组”的结构重排：

```md
# 用户管理

## 功能索引
- [UM-01] 查询筛选
- [UM-02] 列表查看
- [UM-03] 新增用户

## [UM-01] 查询筛选
...

## [UM-02] 列表查看
...
```

## Style Lock

若任务是“更新标注内容”，默认锁定以下视觉规范，除非用户明确要求改动：

- 已有编号样式
- 已有角标尺寸、颜色、偏移
- 已有浮窗宽度、圆角、阴影、关闭方式
- 已有 Markdown 层级和排版规则

更新时只改内容与分组，不随意改视觉参数。

### Annotation UI Defaults

若任务包含“生成角标版标注预览”“在原页面直接增加角标标注”“实现可交互标注说明”，且用户未另行指定视觉方案，默认采用以下交互规范：

- 角标样式使用圆形小红点，尺寸以恰好容纳编号为准，不做大面积遮挡。
- 角标上必须显示编号，编号应与菜单标注文件中的功能编号或顺序号保持一致。
- 点击角标后打开标注说明浮层，并支持显式关闭。
- 说明浮层顶部默认提供下拉选择器，允许用户切换查看同页其他功能点标注。
- 标注说明内容默认支持直接修改，并提供保存入口。
- 若未指定浮层形态，优先使用右侧弹框；只有用户明确要求时才改为居中弹窗或其他形态。
- 保存后的标注内容，默认优先写回代码与对应菜单标注文件，确保修改结果可直接参与后续构建与部署。
- 若页面已存在“保存”按钮，默认将其理解为“保存到代码”，而不是仅保存到本地缓存或浏览器存储。
- 保存动作至少应同步两个目标：当前页面实现中的标注数据源，以及 `.trae/skills/PRD标注助手/标注文件/` 下对应菜单的标注 markdown 文件。
- 当页面实现中的标注内容与标注 markdown 文件存在差异时，更新任务应保持两者同步，避免页面展示与文档说明不一致。

## Annotation Quality Standard

### 必须包含的信息

每个功能组至少要回答清楚：

- 这个功能是给谁用的
- 从哪里触发
- 具体做什么
- 受到哪些条件限制
- 成功后页面怎么反馈
- 失败后页面怎么反馈
- 是否依赖其他配置或权限

### 必须避免的写法

避免：

- “支持增删改查”
- “按设计稿实现”
- “点击按钮后进行处理”
- “具体以接口返回为准”

除非用户明确只要简版，否则说明必须可执行、可实现、可测试。

## Self-Check

输出前，逐项自检。

### 任务边界自检

- 是否先判断了菜单边界？
- 是否把不同菜单拆成了不同文件？
- 是否正确识别为初始化或更新？

### 分组逻辑自检

- 是否按业务功能点分组，而不是按视觉组件聚合？
- 同一组件内的多个业务动作，是否被正确拆分？
- 同一业务目标跨多个页面元素时，是否被正确合并？

### 编号与文件自检

- 同一菜单内编号是否唯一？
- 编号是否尽量稳定，没有无意义重排？
- 功能索引是否与正文一致？

### 内容完整性自检

- 每个功能组说明是否足够替代 PRD 阅读？
- 是否覆盖业务目标、规则、反馈、边界和异常？
- 是否存在模糊标题或空泛描述？

### 更新任务自检

- 是否只更新目标菜单文件？
- 对组件式旧标注，是否按新规则做了必要拆分？
- 删除、下线、迁移的功能是否处理干净？

## Default Output Contract

除非用户另有要求，默认按以下交付结构输出：

1. **菜单清单**：列出识别出的菜单
2. **每个菜单一个文件**：菜单级独立标注说明
3. **每个菜单内一个功能索引**：编号 + 功能名称
4. **每个功能组一段完整说明**：使用固定模板展开
5. **如需页面标注**：将每个功能组挂到对应代表性锚点

## Quick Examples

### 示例 1：同一工具栏

页面顶部包含：搜索框、状态筛选、导出按钮、新增按钮。

正确分组：

- 查询筛选
- 导出数据
- 新增记录

错误分组：

- 顶部工具栏

### 示例 2：表格操作列

操作列包含：查看、编辑、删除、重置密码。

若四者业务目标独立，则拆分为：

- 查看用户
- 编辑用户
- 删除用户
- 重置密码

若“查看 + 编辑”在你的业务里属于同一个流程且说明完全一致，可在充分论证后合并，否则默认拆分。

### 示例 3：弹窗表单

“新增用户”弹窗包含基础信息、角色信息、状态配置。

若它们共同服务于“创建用户”这一业务目标，则作为一个功能组；不要再按弹窗中的字段分成多个编号。
